# Production Safety — боевая база и порядок выката (Урок 7, Задание 6)

## ⚠️ Железное: боевую базу НЕ сбрасываем
В базе — реальные данные людей. На проде ЗАПРЕЩЕНЫ:
- `prisma migrate reset` (стирает всё);
- `seed` с очисткой; массовое удаление строк «для порядка»;
- ручные `DROP/TRUNCATE`.

Разрешено только: **`prisma migrate deploy` ПОСЛЕ бэкапа** (бэкап — `docs/memory/infrastructure.md`).
Миграции — совместимые со старой версией (**expand-contract**: сначала ДОБАВЛЯЕМ колонку/таблицу,
старое удаляем только в СЛЕДУЮЩЕМ релизе, когда новая версия уже везде).

## Порядок безопасного выката
1. **Гейт (автоматика):** `./scripts/deploy-remote.sh` сам гоняет `test:all`
   (Vitest + Playwright e2e против прод-сборки) — красные останавливают выкат.
   Сборка входит в e2e-прогон. Обход разово: `SKIP_TESTS=1`.
2. **Деплой:** тем же `deploy-remote.sh` (rsync → `deploy.sh` на VPS: docker compose
   up --build + `migrate deploy`). Скрипты не переписываем.
3. **Smoke на проде (автоматика + руки):** скрипт сам проверяет, что лендинг и
   `/ai-studio/login` отвечают; затем РУКАМИ 2 минуты: вход → главный флоу
   (файл → графики) → новая фича этого релиза.
4. **Откат, если smoke красный:**
   - **Код:** `git revert <плохой коммит>` → снова `./scripts/deploy-remote.sh`
     (прод собирается из кода — отдельный реестр образов не ведём).
   - **База (если ломала миграция):** восстановить из бэкапа — рецепт в
     `docs/memory/infrastructure.md`.
   - Главное правило: знать, как откатиться, ДО того как понадобится. Не чинить
     «наживую» на сервере руками.

## Когда правок много / миграция рискованная
Поднять staging (копия прода с тестовой БД) — осознанным отдельным шагом, см. урок.
Пока хватает: гейт + smoke + отрепетированный откат.
