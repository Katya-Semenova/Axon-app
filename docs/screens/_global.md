## Auth Guard (защита доступа)

**Middleware у нас НЕТ** — доступ гейтится на самих серверных страницах и в server-actions.

- **Публично (вход не нужен):** маркетинговый лендинг и юр-страницы (корень домена); в сервисе —
  входной экран `/` (холст доступен гостю), `/login`, `/register`, `/forgot-password`,
  `/reset-password`, публичная презентация `/p/[id]`, `/storybook`.
- **Только вошедший:** `/settings` — нет сессии → серверный `redirect("/login")`.
- **Только админ:** `/admin/*` — не-админ → `notFound()` (404, скрываем существование).
- **Холст `/`:** открыт гостю (работа в памяти); **сохранение проекта требует входа**
  (кнопка «Сохранить» → модалка `AuthModal`).
- **Данные пользователя:** server-actions проверяют владельца по серверной сессии
  (`Board.ownerId === userId`) — чужое/несуществующее → пусто (IDOR-защита).
- **Намерение (не реализовано):** вошедший на `/login` или `/register` → редирект на `/`
  (сейчас формы показываются всё равно — см. backlog).

## Роли и доступ

| Роль | Что видит |
|---|---|
| гость | лендинг, холст (в памяти, без сохранения), публичные деки по ссылке |
| пользователь | свои проекты, настройки аккаунта, сохранение/шаринг |
| админ (по env `ADMIN_EMAIL`) | всё то же + `/admin/*` (read-only: список и профили пользователей) |

> Роль в БД (`User.role`) и действия админа (смена роли/блок) — после Урока 7 (backlog).

## Поведение при ошибках сети

- Каждый запрос к API/серверу должен иметь обработку ошибок (никаких «висящих» промисов).
- Сетевая/серверная ошибка → понятное сообщение пользователю:
  - на формах входа/регистрации/сброса — **инлайн-текст** под формой (как сейчас);
  - на действиях внутри приложения — **тост** (`Toast` / `ToastProvider`).
- Никаких unhandled rejections в проде; ошибки логируются в консоль (`console.error`).

## Сообщения об успехе

- Успешное действие формы → подтверждение пользователю:
  - инлайн-сообщение (зелёное, `text-success`) — в настройках/auth;
  - тост зелёного акцента — в приложении; автозакрытие ~3 c; не блокирует интерфейс.
- Текст — из паспорта конкретного экрана (раздел «Сообщения»).

## Loading-состояния

- У каждого async-действия — индикатор загрузки.
- Кнопка на время запроса **блокируется** и показывает спиннер (`Button loading`).
- Списки/карточки при загрузке — `Skeleton` или короткий текст «Загрузка…».

## Защита от двойного submit

- Submit-кнопки блокируются после клика до завершения запроса (`loading`/`disabled`).
- Двойной клик не должен создавать две записи.

## Дата и время

- Показываем в локали пользователя (`toLocaleDateString` / `Intl`); где уместно — относительный
  формат («5 минут назад»).
- В БД храним как UTC (timestamp).

## Язык интерфейса (i18n)

- Сервис двуязычный (`next-intl`, RU/EN): язык по cookie + `Accept-Language`, переключатель в шапке.
- Новый UI — через словари `messages/*`, **без хардкода текста**.
- *Долг:* экраны `login`/`register`/`forgot`/`reset` пока на RU-хардкоде (в backlog).

## Empty State (единый шаблон пустого состояния)

- Иконка (по смыслу экрана).
- Заголовок — одно предложение: что здесь должно быть.
- Описание — одно предложение: как это сюда добавить.
- CTA-кнопка к ключевому действию (напр. «Загрузить первый файл»).

## Приставка адреса (basePath)

- Сервис живёт на `/ai-studio` (`basePath`). Внутренние ссылки через `<Link>` Next дописывает сам;
  «сырые» `fetch`, `next/image` по строке, абсолютные ссылки и ссылки на лендинг (`<a href="/...">`)
  — учитывают приставку вручную (`lib/base-path.ts`). См. [ADR-010](../decisions/ADR-010-app-url.md).
