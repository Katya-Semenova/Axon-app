# ADR-011: Цепочка spec → test → код

## Context
Между сессиями AI «забывает» прошлую логику — без явной спеки он генерирует похожее,
но не идентичное поведение, и фичи незаметно дрейфуют. Регрессии возникают там, где
визуально «всё работает». В проекте уже есть все три слоя (спеки экранов, BDD тест-кейсы,
код), но порядок работы с ними до сих пор не был зафиксирован отдельным решением.

## Decision
Любое изменение поведения проходит три шага по порядку:
1. Сначала обновляем спеку (`docs/spec.md` — общая логика; `docs/screens/<screen>.md` —
   конкретный экран; `docs/screens/_global.md` — сквозные правила).
2. Потом обновляем тест-кейс (`docs/test-cases.md`) — новое ожидаемое поведение
   в формате Дано/Когда/Тогда.
3. Только потом меняем код.

Тесты — black-box: бьют по публичному интерфейсу (HTTP, UI), не импортят внутренности,
поэтому код можно рефакторить, а тест-кейс не ломается. Спека и код разошлись →
чиним ОДНУ сторону до совпадения; источник правды — спека.

Это же правило уже закреплено двумя страховками: железное правило №1/№3 в `AGENTS.md`
и PostToolUse-хук `global-spec-reminder` (см. `docs/automations.md`).

IMPL: docs/screens/
IMPL: docs/test-cases.md

## Alternatives Considered
- Менять только код, без спеки и тест-кейсов: классический путь к регрессиям через 5–10 фич.
- White-box тесты (импорт внутренних функций): ломаются при рефакторинге, ложные срабатывания.

## Consequences
Регрессии ловятся (спека и тест-кейс показывают, что именно сломалось), у AI есть «карта
истины» между сессиями. Цена — чуть больше шагов на простые правки и поддержание
spec/test-cases в актуальности (коммит без обновления спеки считается незавершённым).
