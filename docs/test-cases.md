## Сценарий 1: Регистрация и первый вход
- **Дано:** пользователь не зарегистрирован, открыт `/register`
- **Когда:** заполняет имя, валидный email, пароль ≥ 8, ставит галочку согласия, жмёт «Зарегистрироваться»
- **Тогда:** в БД создаётся `User` с захешированным паролем (не plaintext)
- **Тогда:** редирект на `/` (вход в приложение)
- **Тогда:** cookie сессии — `HttpOnly` (+ `Secure` на проде), ставит Better Auth
- **Тогда:** в шапке вместо «Войти» — аватар (AuthNav)
- **Статус:** ✅ по живой проверке прода (2026-06-19/22). Точные флаги cookie (`Secure`/`SameSite`) — ⏳ перепроверить в DevTools на проде.

## Сценарий 2: Вход с неверным паролем — единый ответ + защита от перебора
- **Дано:** пользователь зарегистрирован
- **Когда:** пытается войти с неверным паролем
- **Тогда:** ошибка «Неверный email или пароль» — **такая же**, как для несуществующего email (защита от перебора аккаунтов)
- **Тогда:** после серии неудачных попыток с одного IP — `429 Too many requests` (rate limit на `/api/auth/*`)
- **Статус:** ✅ единый ответ на входе (security-check 2026-06-17). 🟡 rate limit включён, но мягче рекомендации урока (сейчас 10/60s, советуют 5/мин — в backlog). 🟡 **регистрация** при занятом email отвечает «email занят» (раскрывает аккаунт — принятый компромисс, в backlog).

## Сценарий 3: IDOR закрыт (чужие проекты недоступны)
- **Дано:** два вошедших пользователя A и B; у каждого есть свой проект (доска)
- **Когда:** A пытается открыть проект B по его id (через server-action `getBoard`)
- **Тогда:** данные B **не возвращаются** (проверка `Board.ownerId === userId` → как «не найдено»), не «Forbidden» (это утечка факта существования)
- **Когда:** A пытается изменить/удалить проект B
- **Тогда:** действие отклонено, проект B в БД цел
- **Статус:** ✅ проверено на 2 аккаунтах — `docs/audits/security-check-2026-06-17.md`.

## Сценарий 4: Защита страниц (гейты доступа)
- **Дано:** пользователь не авторизован
- **Когда:** открывает `/settings` напрямую по URL
- **Тогда:** серверный редирект на `/login`
- **Когда:** не-админ открывает `/admin/users`
- **Тогда:** `404` (скрываем существование админки), не редирект
- **Когда:** пользователь успешно входит и снова открывает `/settings`
- **Тогда:** страница настроек доступна
- **Статус:** ✅ **проверено вживую 2026-06-23** (HTTP-запросы к проду, без входа): `/ai-studio/admin/users` → `404`; `/ai-studio/settings` → редирект на `/ai-studio/login`. + гейты по коду (`settings/page.tsx`, `lib/admin.ts`). Доступ к `/settings` ПОСЛЕ входа — ⏳ под вход (часть пользователя).

## Сценарий 5: Главный флоу — файл → инсайты → сохранение → персист
- **Дано:** вошедший пользователь на входном экране `/`
- **Когда:** перетаскивает CSV/Excel в dropzone
- **Тогда:** файл разбирается, на холсте появляются инсайты и дата-сеты (графики)
- **Тогда:** создаётся проект пользователя; он виден в «Мои проекты»
- **Тогда:** после перезагрузки страницы проект и его содержимое на месте (сохранены в БД)
- **Статус:** ✅ смоук + живая проверка (загрузка → инсайты → сохранение → авто-пан) — `docs/audits/persistence-check-2026-06-17.md` + прод 2026-06-19/22.

## Сценарий 6: Публичная презентация по ссылке (share by token)
- **Дано:** владелец собрал деку и в «Показе» создал публичную ссылку `/p/[token]`
- **Когда:** получатель (без входа) открывает ссылку
- **Тогда:** видит деку read-only: листание стрелками/точками/клавишами, без возможности правки
- **Когда:** владелец отзывает ссылку, получатель открывает её снова
- **Тогда:** «Презентация недоступна» (токен невалиден → `deck=null`)
- **Статус:** ✅ шаринг по ссылке + отзыв (Шаг 12). **Проверено вживую 2026-06-23:** битый токен
  `/ai-studio/p/<неверный>` → «Презентация недоступна». Создание/отзыв ссылки вошедшим — ⏳ под вход.
