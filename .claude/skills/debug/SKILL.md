# /debug — баг через гипотезы, не интуицию

Запрещено править код «на глаз» до подтверждения причины. Порядок жёсткий:

## Шаги
1. **Симптом.** Спроси (если не сказано): что делали → что ожидали → что увидели.
   Есть ли сообщение об ошибке / скриншот / шаги воспроизведения.
2. **Гипотезы.** Сформулируй 3–5 КОНКРЕТНЫХ гипотез уровня «обработчик не вызывается»,
   «на вход пришёл пустой массив», «БД вернула null», «состояние затирается вторым рендером».
   Покажи список пользователю.
3. **Инструментация.** Добавь точечные логи (`console.log("[debug] …")` с меткой `[debug]`)
   ровно в местах, различающих гипотезы. Не меняй логику.
4. **Воспроизведение.** Попроси пользователя повторить сценарий (или прогони сам —
   тестом/браузером Playwright MCP, правило одного dev-сервера: `docs/rules/dev-server.md`).
5. **Чтение логов.** Какие гипотезы опровергнуты — вычеркни вслух. Осталась одна
   подтверждённая → только теперь чини. Ни одна не подтвердилась → новый круг гипотез.
6. **Уборка.** После фикса удали ВСЕ логи с меткой `[debug]`. Прогони `npx tsc --noEmit`
   и релевантные тесты. Неочевидную причину зафиксируй находкой (`docs/decisions/findings/`).

## Правила
- Один фикс = подтверждённая причина. «Заодно поправил рядом» — запрещено (правило №6 CLAUDE.md).
- Если баг воспроизводится тестом — сначала красный тест, потом фикс (ADR-011 spec→test→код).
